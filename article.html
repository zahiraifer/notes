Safe to Call Twice: Designing AI-Agent Tools for Retries, Duplicates and Partial Failure

By Zahi Raifer

Every tool you hand to an AI agent will eventually be called twice. A connection drops after the server finished its work, a client times out a little too early, or the model decides to try again. With an agent calling tools in a loop, a double submit is something you design for from day one.

I work on Orivox, an AI website builder for small businesses, where an AI edits live websites for real owners. One of its two front doors is a remote MCP server, so an owner can build and edit their site from their own Claude. That means a model we do not control calls our tools over the internet. This post is about the small set of decisions that make those calls safe to repeat, and safe to fail halfway.

Start from the uncomfortable question

For every tool, I now ask one question before anything else: if this call is made twice, or dies in the middle, what does the site look like afterwards?

For a read-only tool the answer is boring, and boring is the goal. For a tool that writes, there are three outcomes to avoid: a duplicate (two projects where the owner asked for one), a phantom (the agent says it worked when nothing changed), and a tangle (two writes interleaved on the same files). Each design choice below closes one of those doors.

1. Report completion honestly, even when bookkeeping fails

The rule that surprised people most when we wrote it down: a completed write is always reported as done. If the files have been written and a later step, such as usage metering, fails, the MCP tool still returns success.

That can look like hiding an error. It is the opposite. The agent on the other side has no way to know which internal step failed. If we return an error after the real work is already on disk, the most reasonable thing a model can do is call the tool again, and now there are two projects. Returning success describes the world correctly: the thing the caller asked for exists. The metering problem is ours to fix on our side, not something to push back to a client that will "fix" it by repeating the work.

2. Put the irreversible step in the right place

Creating a project through the connector is not one action but a short sequence: check quota, create the project record in the web app, create the files in the editing service, finalize, then record usage.

The order is the design. The cheap check comes first, so a call that should be refused is refused before anything is created. The business record and the files come next. Usage comes last, after the thing the owner asked for really exists. That is what makes rule 1 possible: by the time the only remaining step is bookkeeping, the honest answer to the caller is already "done."

3. One writer per project, for the whole turn

Duplicates are one problem; interleaving is another. Orivox keeps a single project lock in Redis, held for a whole turn by whoever is writing: an edit, a manual commit, a site copy or a background job. Two changes can never interleave on the same site.

The point for retries is that a repeated request does not race the original. It waits its turn, and when it runs, it runs against the site as the first request left it. Pair that with another of our save rules, a page is read before it is written, and a second call is always based on the current page, not on a stale copy someone else's turn already replaced.

4. Keep the server forgetful

The MCP server keeps no session state between calls, so any instance can serve any request. That sounds like an operations detail, but it matters for retries: there is no server-side conversation that a retry can land in the middle of, or that a restart can lose. A restart costs at most the one request in flight, and the next attempt starts clean.

Edit turns and other long work run through job queues backed by Redis, and a web request never waits on a model. A slow model call cannot hold a request open long enough to invite a timeout-and-retry in the first place.

5. Make the unit of change small and addressed

Edits arrive as a list of operations from a grammar of 14 verbs, such as set_text, add_class, insert_after and remove, and every operation names its target by a stable id like [data-ai-id='a0f0']. Python applies the list, runs its checks, and commits the result to the project's Git repository.

This helps with repeats in two ways. First, some verbs are naturally repeatable: setting the same text on the same element twice leaves the page exactly as setting it once. Others, like inserting a block, are not, and having them as named verbs makes that difference visible instead of buried in a rewritten page. Second, every turn is its own commit, so when something does go wrong, undo is a Git restore to a known version, not a reconstruction from memory.

6. The mirror rule: never claim what did not happen

Rule 1 stops false failures. Its mirror stops false successes. One of the deterministic checks on every save is that a claim of success needs a real change: the assistant never reports an edit that did not happen. And only the server decides whether a turn is saved, never the model's description of what it did.

Together the two rules give the caller a simple contract. "Done" means the change exists. "Not done" means it does not. A model can safely make decisions on that, including the decision to try again.

7. Check the whole path from the outside

Unit tests can tell you each step works. They cannot tell you the sequence still works when real sign-in, real networking and a real client are involved. So every five minutes a probe walks the AI connector end to end, from discovery and sign-in to a real tool call, and emails an incident report on any failure and on recovery.

A short checklist

If you are exposing write tools to agents, these are the questions I would ask of each one:

  • If this call succeeds on the server but the response is lost, what does a retry do?
  • Is the last step bookkeeping? If so, does a bookkeeping failure still return "done"?
  • Can two calls for the same resource run at once, or does a lock make one wait?
  • Is a repeat based on the current state, or on a copy that might be stale?
  • Can the tool ever report success for a change that did not happen?
  • Is there any server-side session state a restart would lose?

None of this requires an exotic protocol. It requires writing down, per tool, what "done" means, and then making the code tell the caller the truth about it.
